근거: `HIS 응급관리.uml`, `UD2_응급관리_유스케이스_하위작업매핑.xlsx`, `개발표준가이드.md` 21장.

> **범위 조정 (2026-09-30, UML `01-5 최종`)**: 프로젝트 기간 단축으로 유스케이스를 39개 → 26개로 줄였다. 표에서 ~~취소선~~ 행은 제외된 항목이다(번호는 하위작업 매핑표와 맞추려고 유지).
> 제외: 협진 요청, 당직의 호출, 수술-시술 긴급 요청, 외부 병원 전원 정보 조회, 혼잡도 지표 조회(종합 현황판에 통합), 응급 의료기기 할당, 구급차 이송 기록, 응급업무코드 4종, 동의서 양식 조회, 동의 확인 유예 처리.

## 1. 목표

응급실에서 환자 내원부터 퇴실·전원까지 중증도 평가, 자원 배정, 진료·투여, 모니터링, 타 서비스 연계를 **단일 Bounded Context(EMG)** 로 제공한다.

## 3. 기능 요구사항 요약

### FR-TRIAGE
- 119 사전정보 조회·저장
- KTAS 초기/재평가 이력 관리
- 활력징후·EWS 기록
- 격리 유형 등록·해제 (DUR은 조회만)
- 패혈증/뇌졸중 스크리닝 결과 저장

### FR-RESOURCE
- 구역·병상 마스터 및 배정/해제
- 구역별 혼잡도 지표 산출(종합 현황판에서 사용). 의료기기 할당·NEDIS 연계는 제외

### FR-CARE
- 접수 유입 응급환자 목록 제공(RCP Consumer)
- 진료기록·처치·MAR·CPR 타임라인 기록, 동의 기록(종이 동의서 수령 사실)
- MAR/처치는 GR2 `orderId` 참조 (처방 이중기입 금지)

### FR-ORDER-CHANNEL
- 응급 UI에서 GR2 처방코어만 호출해 처방 생명주기 처리
- LAB/PHM/SUR **직통 오더 생성 금지**
- 협진·당직·수술 긴급 요청은 범위에서 제외

### FR-MONITOR / FR-DISPOSITION
- 현황판(재실·병상·혼잡도)·LOS 알림 생성 배치와 확인 처리
- 퇴실 유형(귀가/입원/전원/사망/DAMA) 결정
- 입원요청·전원소견서 (구급차 이송 기록은 제외)
- 입원요청은 Kafka 이벤트로 병동(IPT)에 직접 전달(`ADMISSION_REQUESTED` → 병동이 `BED_ASSIGNED`/`ADMISSION_REJECTED` 회신), 원무 경유·오케스트레이터 없음. 병상 가용 조회(GET)는 IPT에 동기로 유지. 상세: `flow.md` 7-1장

### FR-REFERENCE (응급 참고 문서 라이브러리)
- 응급 직원이 프로토콜·지침·서식 파일을 환자와 무관하게 찾아 보고(제목·분류·파일 이름 검색), 올리고, 목록에서 뺀다. 별도 화면 `/emergency/reference`(응급 메인의 "Reference Documents" 버튼, 사이드바 메뉴는 admin 메뉴관리에서 등록)
- 파일 본문은 SeaweedFS(S3)에, 목록은 응급 DB에 둔다. 삭제는 상태 변경(파일은 남긴다). 형식은 pdf·이미지·Office·한글로 제한하고 10MB 이하. 상세: `api.md` 2.8장

### FR-CODE
- (제외) EMG 전용 코드 CRUD는 삭제. 코드는 admin 공통코드 캐시를 우선 사용하고 없으면 코드 안 폴백 상수 사용

## 7. 보류한 개선 과제 (합의·요청 후 진행)

### 7.1 오접수·중복 접수 정리 (2026-10-06 논의 → 2026-10-08 접수팀 합의·구현, admin `06` 추가와 DDL 실행 후 사용)

**문제** — 접수가 같은 환자를 중복으로 접수했는데(중복 경고 `GET /care/patients/active`를 무시) 그중 한 건이 잘못 들어온 경우, 응급에서는 접수를 지울 수 없다(삭제는 상태 변경 규칙, 삭제 기능 없음). 정상 절차는 접수가 잘못 들어온 한 건을 취소하는 것이고(응급은 취소 이벤트로 `Cancelled`), 응급 직원이 그 접수에 KTAS·활력징후·병상·처치 같은 기록을 이미 입력했다면 접수의 취소 가능 여부 조회가 `HAS_RECORDS`라 접수에서 취소할 수 없다. 지금은 기록이 있는 접수를 정리할 방법이 없다(퇴실 처리로 닫는 것이 가장 가깝지만 사유 구분이 안 된다).

**합의된 방식(2026-10-08, 접수팀)** — 응급이 퇴실 유형 `06`(오접수·중복 접수)로 접수를 닫으면 Kafka 이벤트 `emergency.reception.voided.v1`(`ReceptionVoided`)을 보내고, 접수가 응급 기록 유무와 상관없이 접수를 취소한 뒤 `ReceptionCancelled`를 보낸다. 규격은 `docs/api.md` 6-2장. 응급은 응급 기록을 지우지 않는다(의무기록 보존, 접수만 닫는다).

**임시 운영 원칙** — 중복 접수를 알게 되면 응급 기록을 입력하기 **전에** 접수에 어느 쪽을 취소할지 알리고, 진료는 남길 접수 한 건에만 입력한다(06 은 이미 기록이 입력된 뒤를 위한 것이다).

**구현한 것(응급)**

| 구분 | 내용 | 상태 |
| --- | --- | --- |
| 퇴실 유형 | `06` 오접수·중복 접수. 응급 폴백 목록(`EmgCodes`, 프론트)에 추가. 최종 결정이라 바꿀 수 없고(DONE), 병상은 퇴실 완료처럼 비운다 | 구현 |
| 사유 | `DISPOSITION.VOID_REASON_TYPE_CODE`(DUPLICATE/ERRONEOUS)·`VOID_REASON`(500자)·`KEPT_RECEPTION_ID` — 06 일 때 사유 유형·사유 필수, 남길 접수는 중복일 때만 선택. 화면은 06 선택 시 입력칸과 확인 창을 보여 준다 | 구현(DDL 실행 필요) |
| 접수에 알림 | 커밋 뒤 이벤트 발행, 토픽 생성, 10분마다 재전송(접수가 아직 취소하지 않은 건, 72시간까지) | 구현 |
| 접수 취소 수용 | 응급이 06 으로 직접 닫은 접수는 접수의 취소 이벤트를 기록·처방이 있어도 받아들임(취소 가능 여부 조회도 `CANCELLABLE`) | 구현 |
| 중복 표시 | 환자 목록 응답에 `patientId` 추가, 같은 환자의 진행 중 접수가 둘 이상이면 목록에 `Duplicate?` 표시 | 구현 |
| 통계 | 오접수 건은 퇴실로 현황판 재실 수에서 빠지고, 접수가 취소하면 취소 상태가 된다 | 구현(별도 통계 화면 없음) |
| 수납 | 응급은 수납과 연동이 없어 확인할 것이 없다(접수·수납 소관) | 해당 없음 |

**남은 일**: admin 공통코드 `06` 추가(월요일 예정) → DDL 실행 → 서버·화면 반영 → 접수와 시험(진료 기록이 있는 접수를 응급이 오접수로 닫기 → 접수 취소 → `ReceptionCancelled` 확인). 운영 전에 토픽 쓰기 권한(ACL) 제한 여부를 브로커 관리자와 정한다.

**요청할 공통코드**: 그룹 `ER_DISPOSITION_TYPE_CD`, 코드값 `06`, 이름 "Erroneous / duplicate registration"(오접수·중복 접수), 사용 `Y`, 정렬 순서 마지막.

### 7.2 미확정 구두 처방이 있는 채로 퇴실할 때의 경고 (2026-10-08 논의 — 경고는 구현함, 기한 관리는 보류)

**현재 동작** — 구두 처방은 응급에서 말로 지시한 것이라 사후에 의사가 확정하는 것이 원칙이다. 응급 서비스는 확정을 처방 시점과 분리해 두었고, **확정하지 않아도 퇴실 결정이 된다**(서버·화면 모두 구두 처방 확정 여부를 확인하지 않음). 퇴실이 끝난 뒤에도 이미 있는 처방의 구두 확정은 허용한다(퇴실 뒤 정리 작업). 미확정 구두 처방은 처방 카드에 `Verbal · Awaiting confirmation` 배지로 계속 보이고, 확정되면 `Verbal · Confirmed by 의사`로 바뀐다.

**문제** — 확정을 잊고 퇴실하면 확정이 영영 남지 않을 수 있다. 퇴실 때 알려 주는 곳이 없었고(→ 2026-10-08 경고를 추가함), 장기 미확정 처방의 기한 관리는 아직 없다.

**하려면 필요한 것**

| 구분 | 내용 | 담당 |
| --- | --- | --- |
| 경고 — **구현함(2026-10-08, 프론트)** | 퇴실 결정 화면에서 "취소되지 않았고, 구두(`verbalYn=Y`)이고, 확정되지 않은 처방"이 있으면 "확정되지 않은 구두 처방이 N건 있습니다. 퇴실 뒤에도 Order 탭에서 확정할 수 있습니다" 안내를 보여준다. **막지는 않는다**(응급은 상황이 급해 막으면 퇴실이 지연될 수 있음). 처방 목록은 화면 저장소(Redux)에 이미 있어 프론트만으로 가능하고 서버 변경은 필요 없다 | 응급(프론트) |
| 확인 — **구현에서 대응함** | 확정된 구두 처방이 처방 목록 응답에 확정 정보(`verbalConfirmedAt`/`verbalConfirmedBy`)까지 실려 오는지 먼저 확인한다(2026-10-08에는 서버의 구두 처방 7건이 모두 미확정이라 비교하지 못함). 목록에 빠져 있으면 새로고침 뒤 확정된 처방을 미확정으로 잘못 경고할 수 있어, 구두 처방만 단건으로 다시 읽어 판단해야 한다. 확인은 시험 환자의 구두 처방 하나를 실제로 확정해 목록·단건 응답을 비교한다. 구현은 이 불확실성을 피해, 처방 목록을 불러올 때 화면이 이미 조용히 읽어 두는 단건 상세(항목 포함)로 확정 여부를 판단하고 상세를 읽지 못한 처방은 경고하지 않는다(`pendingVerbalOrders`, `UnconfirmedVerbalNotice`). 시험 환자의 확정 처방으로 목록·단건 응답을 비교하는 일은 남아 있다 | 응급 |
| 기한 | 일정 시간(예: 24시간) 지나도 확정되지 않은 구두 처방의 알림·목록. 처방 원장이 처방코어라 응급이 직접 집계하지 않고 처방코어에 조회 방법을 확인해야 한다 | 응급 + 처방코어 확인 |

**시연에서의 설명** — 구두 처방은 사후 확정이 원칙이라 퇴실을 막지 않고 확정은 퇴실 뒤에도 가능하게 했다(의도한 설계). 확정 전에는 처방 카드 배지로 표시된다. 퇴실 결정 화면의 미확정 구두 처방 경고는 구현했고(퇴실은 막지 않음), 장기 미확정 기한 관리는 후속 과제다.

### 7.3 재방문 환자의 이전 응급 방문 기록 보기 (2026-10-08 논의, 이후 과제로 보류)

**현재 동작** — 응급의 처치·투약·진료기록·CPR 등 모든 기록은 **접수 한 건(방문 1회)에 붙어서** 저장되고, 화면에는 지금 선택한 접수의 기록만 보인다. 같은 환자가 다시 접수되면 새 접수가 만들어지고 이전 방문의 기록은 보이지 않는다. 환자 ID로 접수를 찾는 조회(`GET /care/patients/active?patientId=`)는 있지만 중복 접수 경고(최근 24시간 안의 진행 중 접수)용이다.

**필요성** — 이번 시연·범위에서는 필요하지 않다. 실제 운영에서는 재방문 환자의 이전 투약·처치와 경과, 며칠 전 같은 증상으로 왔는지를 보는 것이 판단에 도움이 된다.

**지금 구현하지 않는 이유**

| 구분 | 내용 |
| --- | --- |
| 약 부작용·알레르기 | 이전 방문에서 가장 가치가 큰 정보인데, **알레르기·약물 부작용을 담는 곳이 지금 시스템에 없다.** 응급에도 입력하는 화면이 없고, 검사 서비스 등 다른 서비스에도 해당 데이터가 없어 가져올 곳이 없다. 응급이 이전 투약 기록만 보여 주면 "부작용 없음"처럼 오해될 수 있다 |
| 책임 범위 | 환자의 장기 진료 이력은 환자·외래(통합 차트) 쪽의 몫이고, 응급은 방문 단위 실행 기록만 갖는다는 것이 원칙이다. 응급이 전체 이력 화면을 만들 일은 아니다 |
| 신원 불명 환자 | 임시 환자 ID(`무명환자-…`)는 이전 방문과 연결할 수 없고, 정식 환자로 전환된 뒤 ID 연결 방식도 접수팀과 합의되지 않았다 |

**하려면 필요한 것(안)**

1. 알레르기·약물 부작용을 어디서 관리할지 정한다(환자 서비스에 두거나 응급이 입력받는 등 — 데이터 소유 서비스 합의). 응급이 입력받는다면 입력 화면·저장 컬럼(DDL)·공통코드가 필요하다.
2. 응급은 환자 ID로 이전 접수들을 찾아 **이전 응급 방문 요약(날짜, 주호소, 처치·투약 요약)을 읽기 전용으로** 보여 준다. 새로 저장하는 데이터는 없고 응급 DB의 기존 접수·기록을 읽는 조회와 화면이다.
3. 환자 ID가 정확히 일치하는 접수만 묶고, 조회 권한을 확인한다(다른 환자 기록이 섞이지 않게).
